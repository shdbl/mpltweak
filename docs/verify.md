# 写回与验证

## 三层验证

`--write` 不是"盲改"，每一步都可回滚，而且**每一层跑没跑、结果算不算数，JSON 里都如实标**：

1. **语法层**（`layers.syntax`）—— 写盘后**无条件** `ast.parse`（原位与块两条路径都做）：写回只要引入
   语法错误，**当场回滚**，不会留下一份跑不起来的脚本；
2. **重跑层**（`layers.rerun`）—— 无头重跑（只给子进程环境钉 `MPLBACKEND=Agg`）。这一层是**裸跑你的
   脚本**（`writeback.py:4513` 的 `verify_run`：`:4527` 设这个环境变量、`:4531` 直接起 `[python, script]`），
   所以脚本里自己写 `matplotlib.use('TkAgg')` 是**能把它顶回去**的 —— 无头机器上会跑不通，有桌面的
   机器上可能真的弹窗。退出码非 0 时会进一步判别两件事：
   **"工具写坏了"** → 回滚；**"脚本本来就跑不通"**（缺数据 / 缺依赖 / 需要 GUI）→ **默认也回滚 +
   明确失败**（错误里写明"默认**不保留**，要保留请显式 `--keep-unverified`"）；
3. **语义层**（`layers.semantic`）—— 重跑后 dump 目标图状态，与参数里的位置 / 字号 / grid / spines /
   clim 逐项比对；"跑通了但布局没落到目标图"会被判失败。**取不到图状态时这一层是 `null`、`verified`
   也是 `null`**，不再谎报 `true`（人读会明说"只确认了脚本能跑通，**没有**验证布局是否落到目标图上"）。
   这一层（以及采集侧的 `describe` / `check` / MCP）跑在 `python -m mpltweak.verify` 子进程里：脚本在
   子进程内由 `_collect_session` 把 `matplotlib.use` / `plt.switch_backend` 换成**空操作**
   （`verify.py:829-836`）⇒ **Agg 在这里是钉死的**，脚本顶不回去 —— 与上面**重跑层**是**两套口径**。

`--json` 里这三层的状态就是 `layers = {syntax, rerun, semantic}`：`true` = 这一层跑了；
`null` / 缺键 = **这一层没跑**（所以 `verified` 现在可能是 `null` 或 `false`，不再是"恒为 true"）。
块路径另外给 `anchor`（块插在哪：`before` / `after` / `tail`）、`attempts`（每次尝试落在第几行、
成没成）与 `err`（失败原因）—— 出问题时能一眼看出"块插到哪里、为什么没成"。

**脚本自己带参数**（依赖 `sys.argv`，如 `python fig1.py --data x.npz`）：重跑验证的
子进程命令行默认不带用户脚本的参数 → 带参脚本重跑时行为与基线不一致 → 默认回滚 +
误归因"缺数据/依赖"。把参数放在 `--` 后面即可原样透传（bug #6）：

```bash
mpltweak apply fig1.py --write -- --data x.npz --level 3
```

`--` 之后的参数沿 `apply → writeback → verify_run / verify_semantic → 子进程` 全链
原样到达脚本的 `sys.argv`（`verify_semantic` 的子进程用 `--` 分隔，避免被当成工具自己的
开关）；baseline 判别（"脚本本来就跑不通"）同样带上这些参数。**不带 `--` 时行为与以前
完全一致**（命令行不附加任何参数）。

**`--keep-unverified`（自担风险的档位）**：脚本本身在无头环境跑不通时（缺数据 / 依赖 / 需要 GUI），
**默认是不保留**这次写回的 —— 那时验证证明不了这次写回可用，留下坏写回比失败更糟。只有你确实知道
自己在干什么（例如脚本要读一个只有你机器上有的数据文件）才加它保留；此时 `verified: null` +
warning，**请自己跑一遍确认**。

**这是确定性写回的保障机制。** 备份写在**脚本旁边**（`<脚本目录>/.tweak_params/<脚本>.tweak.bak`，
不散落到代码目录）。定位锚点是**脚本**，不是参数文件：用 `--params other/x.json` 写回时，
备份**仍然**落在脚本旁、**不会**跟着参数文件跑到 `other/`；`revert` 也因此**不用**再传同一个
`--params`（0.1.8 放在参数文件旁边的旧位置只会作为"主位置找不到时"的兼容兜底读一次）。
每次 `apply --write` 会留**两份**备份，作用域不同：

| 备份 | 内容 | 谁在用 |
|---|---|---|
| `<脚本>.tweak.bak`（固定名） | **首份优先**：只在**不存在**时创建 ⇒ 保存它**建立那一刻**的脚本内容，之后的写回**不覆盖**它 | 默认 `revert` |
| `<脚本>.tweak.<pid>.bak`（专属副本） | **该次写回之前**的内容（按进程各留一份） | `revert --first` |

`_prune_backups(keep=5)` 会裁掉多余的专属副本，但**永久保留最早那一份**（`writeback.py:2266`：
保留"最近 5 份 + 最早 1 份"，裁掉的是**中间**的）—— 这正是 `revert --first` 还能回到最初的前提。
同一个脚本的写回用 `<脚本>.apply.lock` 串行化，所以两处改动不会"凭空消失"。
慢脚本超时的口径（不算"工具写坏了"、保留写回 + 提示手动确认）集中在下面「写回会跑几遍脚本」一节。

> **可逆范围（按作用域看，别混着理解）**：
> * **默认 `revert`** = 回到**固定名备份里那份**。因为它是首份优先的，连着写回几次之后
>   `revert` 回到的通常就是**你第一次改这张图之前**的原件（**不是**上一步的中间态）。
>   实测：独立进程连续 3 次写回（字号 10→11→12→13）后 `revert --write` → 回到 **10**。
> * **`revert --first`** = 回到**最早那份专属副本**（最早那次写回之前）。上例同样回到 **10**；
>   两者内容在常见情况下相同，差别在于：固定名那份可能被删（或它建立得比 pid 副本更晚），
>   而 `--first` 依赖 pid 副本（见下面边界二 / 三）。
> * **首份优先**说的是**固定名备份的创建规则**（跨独立 `apply` 调用也成立），**不是**"每次写回都
>   重备一份"。
> * **边界一**：专属副本只保留最近 5 份 + 最早 1 份 ⇒ 连续写回很多次后，**中间**某一档
>   （比如"第 3 次之前"）可能已被裁掉，但**最早那份仍在**（实测 7 次写回后第 2 老的那份被裁、
>   最早那份还在，`--first` 照样回到原件）。
> * **边界二**：专属副本写不出来时（典型是 Windows 长路径 MAX_PATH），写回会打 warning
>   （"`revert --first` 将没有可用副本，请用默认 revert"），此时 `--first` **明确失败 `rc=2`**
>   并打印原因 —— 历史版本曾"回落到固定名备份却仍报 `first: true`"（`writeback.py:2291` 记的
>   就是这个现场），**现在已改为响亮失败**（`revert.py:158-176`），不会拿中间态冒充"最早"。
> * **边界三**：同一个进程里连续写回（MCP / agent 调用）pid 相同 ⇒ 专属副本被同一文件名覆盖，
>   那时 `--first` 可能只回到**该进程最近一次**写回之前（反而比默认 `revert` 更"新"）。
> * **建议**：要长期可逆（回到很久以前的任意一档）就用**版本管理**（git）或自己另存一份，
>   别只依赖 `.tweak_params/` —— 它只是"最近这几步"的安全网。

写回是**原子替换**（先写临时文件再 `os.replace`），所以脚本不会出现"改到一半"的状态；
代价是**文件 inode 会变**：如果你用硬链接指向这个脚本，替换后链接仍指向旧内容。
软链接不受影响，文件权限位会被保留。

**人读输出**：成功路径默认**只报一行**
（`[OK] 已原位写回 3 处（fig1.py）；图已更新（重跑 + 语义验证通过）`）；逐处清单、备份路径，
以及上面那几层的逐条结论（"Agg 重跑验证通过" / "语义验证通过"）都在 `-v / --verbose` 里。
**失败、回滚、降级（`--verify-fast` / `--no-verify`）与"未判定"（`verified: null`）不加 `-v` 也照旧全部打出来** ——
收敛的只有成功路径。`--json` 的字段集不受人读输出收敛影响（那才是机器通道的订阅契约）。

## 一次真实写回：完整输出样张

以快速上手那个 `fig1.py`（`add_axes([...])` 写的是字面量）为例，`mpltweak apply fig1.py --write` 的真实输出：

```text
  正在验证（子进程重跑脚本，最长 300s）
[OK] 已原位写回 3 处（fig1.py）；图已更新（重跑 + 语义验证通过）
```

上面就是**真实一次写回**的输出（路径省了目录前缀；你看到的会是绝对路径）。其中"重跑 / 语义验证"是在**你的环境**里把脚本真跑一遍得到的 —— 跑不起来、或图上位置字号与参数不符，都会回滚（见上面的「三层验证」）。

要看**逐处清单 / 备份路径 / 验证分层结论**，加 `-v`（成功路径的细节都在这里；失败与降级信息不加 `-v` 也会打）：

```text
[OK] 已原位写回: fig1.py
  原位修改 3 处: ax0.pos, ax1.pos, ax2.pos
  备份: .tweak_params/fig1.tweak.bak
  [OK] Agg 重跑验证通过
  [OK] 语义验证通过（目标图状态 == 参数）
```

**脚本自己带参数时**（依赖 `sys.argv`，比如平时敲的是 `python fig1.py --data x.npz`）：把参数放在 `--` 后面，写回的重跑验证会**原样透传**给脚本，保证重跑与基线一致、不误回滚：

```bash
mpltweak apply fig1.py --write -- --data x.npz --level 3
```

## 原位改数字，还是插入调整块：两条路 + 两个开关

写回有**两条路**：源码里写的是**字面量** → **直接改那几个数字**；位置来自 `plt.subplots()` / `plt.subplot(1, 2, n)` / `GridSpec`（源码里本来就没有那几个数字）→ **插入一个自包含的调整块**。**能不能插块，取决于目标能不能静态证出**：证不出就 `applied=false`、**不写盘**，只给你一份可粘贴的手改片段。

还是那个 `fig1.py`。**动手前**（手写的数字，通常都不齐）：

```python
ax1 = fig.add_axes([0.08, 0.66, 0.30, 0.21])
ax2 = fig.add_axes([0.11, 0.38, 0.30, 0.21])
ax3 = fig.add_axes([0.05, 0.08, 0.30, 0.21])
```

**你拖完之后**（`mpltweak apply --write` 的结果）：

```diff
-ax1 = fig.add_axes([0.08, 0.66, 0.30, 0.21])
+ax1 = fig.add_axes([0.08, 0.655, 0.300, 0.215])
-ax2 = fig.add_axes([0.11, 0.38, 0.30, 0.21])
+ax2 = fig.add_axes([0.08, 0.380, 0.300, 0.215])
-ax3 = fig.add_axes([0.05, 0.08, 0.30, 0.21])
+ax3 = fig.add_axes([0.08, 0.085, 0.300, 0.215])
```

代码里写的就是字面量，所以**只动了这几个数字**：没有新增一行、没有加 `import`、没有引入任何依赖。字号、图例位置、网格、colorbar 同理，改的都是你代码里原本就有的参数。

想只走一条路：

```bash
mpltweak apply fig1.py --write --style inplace   # 一处都不插块；写不了的字段 rc=1 明确失败
mpltweak apply fig1.py --write --style block     # 一律插块
```

**调整块的真实形态**（上下两行 `auto layout` 标记、里面写了什么、为什么那么写）见 [params.md 的「原位改数字，还是插入调整块」](params.md#原位改数字还是插入调整块)；块的插入点硬约束与"写回被整体拒绝"见下面两节。

## 写回会跑几遍脚本

**为什么必须真的跑**：写回的验证不是静态检查 —— 它要**把你的脚本再执行一遍**，才谈得上"改完这版是能用的"。
语法层是 `ast.parse`（不执行脚本），但**重跑层与语义层都要真的跑脚本**。

**今天会跑几遍**（0.1.10 当前行为）：

| 情况 | 跑几遍 | 每一遍做什么 |
|---|---|---|
| 一切正常（原位路径：源码里有可直接改的数字） | **1 遍** | 这一遍**同时**回答两件事：脚本还跑得通吗（重跑层）、你要调的字段真落到**目标图**上了吗（语义层）。取数方式是脚本写盘那一刻钩住 `Figure.savefig` 抓一份快照、并按创建顺序持住图对象 —— 两者都**不改脚本行为** |
| 目标图取不到状态（脚本没画这张图 / 从没 `savefig` / 子进程没留下状态） | **回退 2 遍** | 第 1 遍没给出结论时**绝不改判据**：第 2 遍按**原样**重跑，判定"还跑得通吗"；语义层如实记为"没有验到"（`verified: null`）。**回退原因会打出来**：`单遍验证未取到目标图状态（…）→ 已回退到两遍口径…` |
| 需要归因"是不是脚本本来就跑不通" | **最多 3 遍** | 再多跑一遍**备份里的原脚本**做基线对照（缺数据 / 缺依赖 / 需要 GUI 这类）。这一遍在**备份**上跑，不计入 `verify_passes` |
| 要**插调整块**（源码里没有可直接改的数字） | **每个候选插入点 1 遍**（通过即止） | 会**逐个候选插入点惰性重试**：每试一个候选就跑**一次**脚本（`_verify_script` → `verify_once`，这**一遍**同时回答"还跑得通吗"与"字段落到目标图上了吗" —— 语义比对用的是这一遍抓到的状态，**不额外起进程**）；**通过就定下这个候选、不再试下一个**（候选循环见 `writeback.py` 的 `for cand in cands:`），只有这一遍判不过（语义不一致）才换下一个候选 ⇒ **常规情形（第一个候选就成功）= 1 遍**；总遍数随**尝试次数**走，不是一个固定值 |
| 参数里有**"原位写不了"的字段**（`grid` / `spines` / `clim` / `pos` / `xscale` 这类，很常见） | **先额外跑 1 遍**（与其它几行**分开计**） | 判"到底要不要退块"只能**实测**：`_pending_vs_live` 跑一遍脚本取实测状态、再与参数逐字段比（`writeback.py:3041` → `:2851`）。**有这类字段时总遍数 = 其它行 + 1**；若各字段与源码现值本就一致（干净往返），常就到此为止（结果 `no_change`、没有主验证那一遍）。**这一遍不计入 `verify_passes`**（它只数主验证的遍数：`writeback.py:3179` / `:5095`）。`apply --write --dry-run` 会跑脚本也正是这一遍 |

默认这一遍还要对账**磁盘上那张图**：图上必须体现这次改动（图没变同样判不通过）；这一遍跑不出结论时
才回退到"原样重跑 + 语义取数"的两遍口径，且回退原因进 warnings（见上表第 2 行）。

**这几遍都在你拿回控制权之前发生**：正常情况等待约等于**单次运行的时长**（比旧口径少整整一遍）；
参数里有上表第 5 行那类"原位写不了"的字段时会**先多跑一遍**（哪怕最终什么都没改也照跑，那种情况下
它就是唯一的一遍）：真有改动要落地时等待是单次的 **2 倍起**，走到回退或归因时回到 **2~3 倍**
（块路径还要按尝试次数叠加）。而且它们**会真的执行你的脚本 ——
脚本里的 `savefig` 照常产出你的图**（多数情况下你因此**不必再单独跑一次**）。

**机器可读通道**：`apply --json` 的每条 `files[]` **恒有**这两个键 ——
`verify_passes`：**1** = 默认单遍 / **2** = 已回退到两遍 / **0** = 这次没有为验证重跑脚本
（`--no-verify`、`--verify-fast`、预览、没有可写字段）。它**只数主验证的遍数**：上表第 5 行"先额外跑的那一遍"
**不计入**，所以 `verify_passes=1` 不等于"整条命令只跑了 1 遍脚本"。**`0` 不是失败**，它只表示"这一档没有为验证重跑脚本"，
与提示语里的「没有重跑脚本 —— 不保证能跑通、也不保证布局真的落到目标图上」是同一口径；
`semantic_basis`：**`live+savefig`**（图对象状态 + 磁盘那张图的追加判据）/ **`live`**（只有图对象状态）/
**空串**（这次没有语义判定依据）。要判断"这次为什么回退"，看 `verify_passes=2` 再读同一条目的 `warnings`。

**超时口径**：重跑默认 **300 秒**（`--timeout 600` 之类可放宽）。**超时不算"工具写坏了"**：拿不到结论时
**不回滚**，而是保留这次写回并打一条 warning（`验证超时（>300s），未能自动验证；脚本保持写回后的状态`），
请你手动重跑确认；语义取数所在的子进程另有自己的上限（默认 **600 秒**，环境变量 `MPLTWEAK_TIMEOUT` 可调）。

**脚本本身在无头环境跑不通时**（缺数据 / 缺依赖 / 需要 GUI）：**默认回滚**，错误里会写明"默认不保留"；
只有你确实知道自己在干什么（例如数据只有你机器上有）才用 `--keep-unverified` 保留 —— 此时 `verified: null`，
**请自己跑一遍确认**。

想完全跳过重跑：`--no-verify` —— 但那等于关掉唯一的安全网。嫌慢：`--verify-fast`（只查语法、不重跑，
见下面「慢脚本」）。

## 后悔了：`mpltweak revert`

写回错了、或者拖完发现还是原来那版好看？不用去翻备份：

```bash
mpltweak revert fig1.py            # 只预览：会改回哪几行（默认，不动代码）
mpltweak revert fig1.py --write    # 真的回退（回到固定名备份里那份）
mpltweak revert fig1.py --write --first   # 回到"最早那次写回之前"（读最早的专属副本）
```

它用的就是**脚本旁边**那份备份（`<脚本目录>/.tweak_params/<脚本>.tweak.bak`，每次
`apply --write` 之前自动留的）。备份锚在**脚本**上，所以写回时用了 `--params`，回退**不用**再传一遍
（旧位置只在主位置找不到时当兜底读一次）—— 可逆范围按作用域分三种，别混着理解：
① **默认 `revert`** 回到**固定名备份里那份**：它是**首份优先**的，连着写回几次之后回到的通常就是
**你第一次改这张图之前**的原件；② **`revert --first`** 回到**最早那份专属副本**（最早那次写回之前），
两者常见情况下内容相同；③ **首份优先**说的是**固定名备份的创建规则**，不是"每次写回都重备一份"。
边界（专属副本只留最近 5 份 + 最早 1 份、副本缺失时 `--first` 明确 `rc=2` 失败、同进程 pid 复用）
与实测数字见上面「这是确定性写回的保障机制」那段。
**revert 自身也可逆**：覆盖前会把当前版本另存为 `<脚本>.revert.bak`（也在脚本旁边的
`.tweak_params/` 里），所以手滑了还能再回去。
恢复是**字节级原样复制**（BOM / 换行 / 编码都不动）。

## 慢脚本：`--verify-fast`（快速档）

脚本要跑几分钟、你只是想先看一眼结果，可以用快速档：

```bash
mpltweak apply fig1.py --write --verify-fast
```

**它的检查范围**：源码仍然是合法 Python（语法错误当场回滚到批前状态）。

**它不检查什么**：**没有重跑脚本** —— 不保证脚本能跑通，也不保证布局真的落到目标图上。
所以它只适合"先快速落实、马上自己跑一遍看图"的迭代过程；正式落实请去掉这个开关。
`--json` 里会如实标 `"verify_mode": "fast"`、`"verified": null`、
`layers = {syntax: true, rerun: null, semantic: null}`；**人读输出也会明说**：
`[!] 快速验证：只检查了语法（源码能被 Python 解析，写坏会当场回滚）。没有重跑脚本 —— 不保证能跑通、也不保证布局真的落到目标图上。正式落实请去掉 --verify-fast`
—— agent 和你都一眼能看出来这份结果没经过重跑。

不确定"这个脚本重跑得起来吗"时，不用先猜：`apply --write` 在重跑之前会做一次
**可重跑预检**（静态看源码，**不执行脚本**），命中「缺依赖 / 需要参数 / 联网 / 等人输入 /
要弹窗」时打一段提示并给出可照抄的下一步（预检只在真写回时才做：`--no-verify` / `--verify-fast` /
`--dry-run` 下不提示；干净脚本零噪音）。
判据与 `--json` 字段见 [exec-boundaries.md](exec-boundaries.md#写回之前的可重跑预检0110)。

## 接进 CI：`--strict`

`check` 默认把布局引擎冲突（`constrained_layout` / `autolayout`）当**提示** —— 那是 matplotlib 的正常写法。
如果你的项目要求"别用会被引擎覆盖的布局方式"，加 `--strict` 让它变成**问题**（退出码 1）：

```bash
mpltweak check fig1.py --strict            # 有布局引擎冲突就 rc=1
mpltweak apply fig1.py --write --strict    # 有冲突时拒绝写回（要放行加 --allow-layout-conflict）
```

`check --json` 也是天然的 CI 用例（`ok` 字段 + 退出码）。注意 **`check` 一次只接受一个脚本** ——
`mpltweak check figures/*.py` 会被 shell 展开成多个位置参数，argparse 直接报
`unrecognized arguments` 并 `rc=2`（实测）；在 cmd.exe 这类**不展开通配符**的 shell 里，则是
`[check] 找不到脚本: …\*.py` + `rc=2`。所以批量要自己循环：

```bash
# 单个脚本：退出码就是门禁（有 jq 时也可以顺手看 ok 字段）
mpltweak check fig1.py --json | jq -e '.ok'
```

```python
# 一批脚本：存成 check_layout.py 再运行（不依赖 jq，Windows / macOS / Linux 通用）
import glob, subprocess, sys
bad = [f for f in sorted(glob.glob('figures/*.py'))
       if subprocess.run(['mpltweak', 'check', f, '--json']).returncode != 0]
print('layout check failed:', bad)
sys.exit(1 if bad else 0)
```

**贴边文字与 `bbox_inches='tight'`**：check 只比较文字外框是否落在 figure 框内，
**不读** `savefig(bbox_inches=...)`；识别到
`bbox_inches='tight'` 就**降级为提示**（`rc=0`；`--json` 里 `tight_bbox: true`、该条
`downgraded: "tight_bbox"`），要按旧口径严判加 **`check --no-tight`**（这个选项**只有 `check` 认** ——
`apply` / `describe` / `revert` 给了是 `rc=2`）。实测
（`audit_018/promo/t14_verify.log` —— **本地记录，未随仓库发布**，可重跑入口 `python tests/test_check.py`）：同一段越界文字，无 tight 时 `rc=1` / `error`，
有 tight 时 `rc=0` / `warn`。

**`--tol` 只收有限正数**：`inf` / `nan` / `<= 0` 会让几何检查静默失效，现在直接拒绝并说明原因
（`rc=2`：`容差必须是**有限正数**（收到 inf）：inf / nan / <= 0 会让几何检查静默失效
`）。

CI 还有一条更省事的静态门禁：`mpltweak check fig1.py --static`（**不执行脚本**，见「执行边界」）。

## 调整块的插入点硬约束与"写回被整体拒绝"

**块的插入点有硬约束**：脚本里有 `savefig` / `show` 时，调整块**只允许插在最后一个 `savefig` / `show`
之前** —— 插在它后面等于"你调的布局根本没进图"，而这正是最难发现的一类事故。行内复合语句
（如 `if flag: fig.savefig("o.png")`）会把插入点**提升到那条语句之前**；找不到合规插入点就**拒绝写回**
（`reason=fail`、脚本一个字节都不动），不会再出现"报成功、你的 PNG 却没变"。实测
（实测）：`if flag: fig.savefig("o.png")` 在第 76 行时，块落在第 9–75 行、
`anchor="before"`、`attempts=[{"anchor": "before", "line": 9, "ok": true, "semantic": true}]`。

`--style` 有两条路。`auto`（默认）能原位改就原位，改不了就退到插入调整块；`inplace`（显式）要求原位，改不了就 `rc=1` / `applied=false`，不假装都改好；`block` 一律插块。
判读落地情况看 `apply --json` 的 `files[]`：`needs_block`、`pending`、`inplace_pending` / `inplace_needs_block`、`auto_fallback`、`inplace_changes` / `inplace_reason`。
逐字段含义与三种风格的实测对照（rc / JSON）见 [params.md](params.md)。

## 调整块的写法与取舍

[params.md 的「原位改数字，还是插入调整块」](params.md#原位改数字还是插入调整块) 给的是块的真实形态与两条最小示例；块内的**写法与取舍**在这里：

- **目标写成静态可证的表达式**：块里逐轴一行，目标用 `axes[0, 0]` 这类**字面量元素**写法。
  **不用运行期下标** —— `fig.axes[i]` / `plt.gca()` / `plt.gcf()` 是"运行时才知道指向谁"的写法
  （运行期下标还可能指到 colorbar / inset 轴），工程上已不再使用。
- **能不能插块取决于目标能否静态证出**：`fig, axes = plt.subplots(2, 2)` 之后用 `axes[0, 0]` 定位可以落地；
  把轴**解包 / 放进循环**里用（`for i, ax in enumerate(axes.ravel())`）或建图形状不是字面量时，
  按 **fail-closed** 处理 —— **不写盘、`applied=false`**，只给一份可粘贴的手改片段。
- **块里钉的是"整份状态"**：开窗导出的是当时的整体状态，所以连"恰好等于默认值"的字段也会被写死
  （例如 `axes[0, 0].lines[0].set_linewidth(1.5)`）—— 想少改就少给（只给真正要改的项）。

## 它到底改了什么

> 上面这两行英文标记就是**实际写进你脚本的那两行**（`# ===== auto layout (generated) - do not
> edit inside =====` … `# ===== end auto layout =====`），不是示意。早期的中文标记
> （`# ===== 自动布局调整…`），工具也**仍认得**并会整体替换，但新写的块一律用英文这两行 —— 想 grep
> 自己脚本里的块，请用 `auto layout`。

- **平时的零侵入**：不加 `import`、脚本里不留任何工具痕迹、不生成副文件；开窗只写参数。
- **写回是你主动要求的动作**（`apply --write`），它本来就要改代码 —— 问题在**改多少**：
  开窗导出的是**当时各轴的实测状态**（每个轴的 pos / 字号 / 网格 / spines / 线宽 / 图例 /
  xlim），直通写回会把这一整份**钉进源码**。实测：一个 8 行的 `plt.subplots(2, 2)` 脚本被插进
  30+ 行的块，连"当时恰好是默认值"的那些字段也一起写死（以后改脚本里的默认值就不生效了）。
- **只给"代码里确有写法"的等值参数 = 不改源码**（实测）：只传 `index` + `pos`（可选
  `figsize_in`）且值与原图一致时，`apply --write --verify-fast` 报 `reason=no_change`、
  `changes=[]`、字节不变（`audit_018/promo/t14_verify3.log` —— **本地记录，未随仓库发布**，可重跑入口 `python tests/test_writeback.py`）。
- **代码里没有写法的字段，等值时也不再插块**（退块判据是**逐字段三态**，见「`--style` 与 JSON
  字段」一节）：只有"有目标值 ∧ 与源码现值不同 ∧ 原位写不了"的字段才会退块。实测 `pos` 等值 +
  `title_fontsize: 12.0`（源码里没写 `fontsize=`），以及 `label_fontsize` + `tick_fontsize` /
  `spines` / `grid` / `xscale` / `figsize` 等值 → `reason=no_change`、不插块、`sha256` 不变
  （复现：`audit_018/promo/t16_verify.log` —— **本地记录，未随仓库发布**，可重跑入口 `python tests/test_writeback.py`）。反向对照（**值确实不同**）仍退块并把值落到图上：
  `title_fontsize: 20.0`、`tick_fontsize: 7.0`、`spines={'top': False}`（同日志）。
- **`describe → apply` 直通依然可能"改代码"**：只要参数里带了**确实不同**、而源码里又写不了的字段，
  它就会插入调整块（那正是"落地"的方式）。所以别把直通写回当成"无需改动"，写回后看一眼 `git diff`。
- **`--verify-fast` 下这条更保守**：它不重跑脚本，证明不了"某字段与源码现值相等"，源码里没有可比写法
  时会退块（详见「给 AI / agent 的排版接口」一节）。
- **只想改你要的字段**：参数写成最小形态
  `{"version": 4, "script": "fig1.py", "axes": [{"index": 0, "pos": [0.07, 0.54, 0.44, 0.40]}]}`。
  只有参数里**显式**给出的字段才会写回（缺 `grid` 键不再被当成 `false` 补上；实测
  记录 `audit_018/promo/t14_verify.log`（**本地记录，未随仓库发布**，可重跑入口 `python tests/test_writeback.py`）的"最小参数"一条：`ax.grid(True)` 原样保留、未出现
  `grid(False)`）。
- 写回前先 `mpltweak apply fig1.py`（只读预览，**不会执行**脚本）或 `git diff` 看一眼。
